# Reproducing the evidence

Run only against isolated synthetic installations. Tests intentionally create orders, modify fixture rates and invoke mock payments/refunds. They are never an operator's production smoke-test script.

The recorded environment uses a Docker network `gc-test`, MariaDB 11 and official WordPress CLI images with PHP 8.3.36/8.5.12. WordPress source is pinned to GitHub WordPress/WordPress tag 7.1.4; the complete WooCommerce release ZIP is 11.2.2, Yoast release ZIP 28.8. Exact image digests are in `evidence/docker-images.txt`.

Prepare two directories under `runtime/site1`, `runtime/site2` with separate wp-config files, database names `gold1`, `gold2`, unique WP salts and independent writable wp-content. Place the three package directories under plugins/themes, or install their ZIPs with WP CLI. WP core source can be shared read-only; per-install configuration, uploads, database and sessions must remain separate. The PHP web entry-point files must be local copies, not symlinks whose `__DIR__` selects the wrong wp-config.

The existing harness paths mount this repository as `/project`; CLI container names are `gc-site1`/`gc-site2`, working directories `/project/runtime/site1`/`site2`, local web ports 8081/8082. Keep `wp-admin` as a local per-install directory too: its relative bootstrap also must resolve the correct wp-config. Containers must receive `GC_DB_PASSWORD` through a protected environment. Generate an ephemeral `runtime/credentials.json` with db_password, admin_password, and a random 32-byte-hex load_secret if running load tests; do not commit or distribute it. The DB root password is test-only and must never be reused.

Install WP, activate Woo/Core/Connector/theme, enable HPOS and run `wp eval-file /project/fixtures/install-sample.php --use-include`. This explicitly approves converting fixture checkout pages to classic. The admin user in these isolated tests is id 1. Unit tests run with plain PHP and need no WP; other PHP files use `wp eval-file ... --use-include` because WP CLI's default eval mode is incompatible with strict_types at file start.

Run `bash tests/run.sh`. Browser tests use Chromium and playwright-core; set GC_PLAYWRIGHT_MODULE/GC_CHROMIUM/GC_PROJECT_ROOT as needed for `browser.cjs`. For the axe test, `npm ci --prefix tools/a11y --cache <private-temp-cache>` uses the included lockfile. Adapt its module/browser paths if not using the managed environment. `security.php`/`extended.php` emit separate JSON for each PHP version. `concurrency.py` starts two actual independent WP CLI workers. `zip-install.py` creates `gold_zip` and installs packages from ZIP; `restore.py` creates `gold_restore` and compares source/restored financial data and application files. Generated DB dumps/configs stay under ignored runtime, excluded from the delivery ZIP.

Load tests: PHP's built-in server uses `PHP_CLI_SERVER_WORKERS=8` on 2 CPU quota cores/8 GiB shared memory. Install `tests/load-adapter.php` only as a local fixture MU plugin and define GC_TEST_HTTP_SECRET from the generated load secret. Seed a hidden virtual product with price MANUAL_FINAL=100 IRR and stock 1000000, store its id in `gc_load_product`. POST test routes authenticate with X-GC-Test; the fixture uses real Gold/Woo services but bypasses public anti-abuse/customer authentication deliberately. Run `python3 tests/load.py` and `python3 tests/load-monitor.py` concurrently. Each phase is a burst, one request per virtual user, not a sustained arrival-rate simulation or a real bank/Agah performance certification. Criteria, response codes, P95 and throughput appear per row. Preserve failed historical evidence when a bug is corrected and rerun all affected cases.

Performance-lab measurements are local Chromium samples. `eventDuration` is a sampled interaction duration, not field INP. A deployed host, real mobile network and real users are necessary for field Core Web Vitals and a commercial capacity SLA.
